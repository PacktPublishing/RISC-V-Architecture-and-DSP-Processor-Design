1. Differences between FDM320RV335 and TMS320F28335

1.1. Creation of startup files

TMS320F28335 uses the hex2000.exe tool to convert the .out file generated by the project into a boot file format.

FDM320RV335 uses the built-in elf-to-bin tool in the integrated development environment.

1.2. Code Security Module CSM

1.2.1. Locking after modifying the password region

In the FDM320RV335 chip, under simulator debugging state, after modifying the values in the password region 0x67fff0~0x67ffff, the chip can be put into a secure protection state by reading the password region / forcing lock / on-chip flash configuration, etc. At this time, the simulator will not disconnect.

Competing chips will disconnect the simulator when switching to the secure protection state.

This difference does not affect the normal operation of the FDM320RV335 chip security protection mode.

1.2.2. Locked state

The FDM320RV335 chip memory space is divided into PMEM and DMEM, used to store code and variables respectively. PMEM is a secure area and protected, DMEM is a non-secure area. After the chip is locked, since the secure area cannot be accessed, the PMEM storing code cannot be accessed, and only the DMEM storing variables can be accessed, thus code debugging cannot be performed.

TMS320F28335 memory is divided into L0~L7, without distinction between PMEM and DMEM. L0~L3 are secure areas, L4~L7 are non-secure areas. After locking, L4~L7 can still be accessed for code debugging.

1.3. Address alignment during memory access

The FDM320RV335 chip requires address length and data alignment for bus access. The smallest address inside the processor is byte address (8-bit), while competing chips use word address (16-bit).

When performing bus access, attention should be paid to the difference in offset addresses between FDM320RV335 and competing chips.

1.4. High-Resolution Pulse Width Modulator (HRPWM) module

The step size of the micro edge positioner (MEP) varies according to worst-case process parameters, operating temperature, and voltage. The MEP step size increases as voltage decreases and temperature rises, and decreases as voltage increases and temperature decreases. TMS320F28335 provides a Scale Factor Optimizing Software (SFO) for applications of the High-Resolution Pulse Width Modulator (HRPWM) module. The SFO function helps dynamically determine the number of MEP steps per synchronous output cycle during HRPWM operation.

FDM320RV335 does not provide this function. It is recommended to evaluate the required counter values in advance under specific operating conditions.

2. Development tools

TI's IDE (Integrated Development Environment) CCS and RV335 are both based on the Eclipse framework, and are generally similar in use, but there are some differences. Here we list some differences that may be encountered during development in software usage.

2.1. Project creation and structure

The project creation wizard of TI's IDE and RV335's IDE differ slightly in interface organization, but the information to be filled in is roughly the same, mainly including project name, directory, product model selection, toolchain selection, etc. One difference is that CCS requires specifying the simulator model, while RV335 uses jlink as the default simulator, so it is not necessary to specify the simulator model here.

After project creation, the generated project templates and structures differ. TI generates a .ccxml file for configuring simulator connection-related content, while RV335 does not have this file. Simulator connection configuration is under Debug Configuration, and connection checking is in the menu Tools => Test Connection. TI uses .cmd files for linker configuration, while RV335 uses .ld files in standard C linker format. In addition, after creating an RV335 project, some peripheral library files are automatically generated for user convenience.

2.2. Build configuration

In CCS, build-related configuration is under right-click project => Properties => Build. After expanding, you can see Compiler, Linker, and Hex Utility sub-items. In RV335 IDE, project configuration is unified under right-click project => Properties => C/C++ Build => Settings. After opening Settings, further configuration for Compiler, Assembler, and Linker can be done on the right side.

2.3. Debug configuration

Debug Configuration opens the debug and run configuration interface. There are some differences between TI and RV335 configuration interfaces. TI uses the Main Tab to specify connection-related configuration, while RV335 uses the Target Tab. TI uses the Program Tab to specify the project to debug and run, while RV335 uses the Main Tab. TI's Flash configuration page is under Target / Flash Setting, while RV335 IDE directly provides On-Chip Flash as a Tab.

2.4. Tool-related

TI uses the Hex2000 tool to convert executable files used for debugging into Hex files for boot.

RV335 provides the elf2bin tool to convert executable files into bin files for boot. elf2bin can be found in the tools folder under the IDE installation directory, or can be opened via the IDE toolbar Tools => Elf2Bin Tool.

3. Programming model differences

To facilitate user migration from TI to the RV335 platform, we developed the ti2rv conversion tool. This document also lists some differences in programming and code logic between the two platforms that may be encountered during development, for reference to enable smoother migration.

3.1. Inline assembly statements

TI inserts commonly used assembly instructions into C code through macros combined with inline assembly, enabling better control of underlying hardware. RV335 maintains similar usage habits, but since RV335 is based on the RISC-V architecture, its assembly instructions are not compatible with TI. The following instructions need to be replaced.

• TI “ESTOP0” replaced with “EBREAK”

// Ti
#define ESTOP0 asm(" ESTOP0")

// RV335
#define ESTOP0 asm("EBREAK")

• TI “EALLOW”, “EDIS”, “clrc DBGM”, “setc DBGM” replaced with “NOP”

// Ti
#define ERTM asm(" clrc DBGM")
#define DRTM asm(" setc DBGM")
#define EALLOW asm(" EALLOW")
#define EDIS asm(" EDIS")

// RV335
#define ERTM asm(" NOP")
#define DRTM asm(" NOP")
#define EALLOW asm(" NOP")
#define EDIS asm(" NOP")

• TI “IDLE” replaced with “WFI”

// Ti

3.2. Interrupt mechanism

TI uses PIE to implement interrupt control, while RV335 uses PLIC. There are some differences in interrupt configuration and usage.

• TI interrupt service functions must be declared with __interrupt, while RV335 does not require it.

// Ti
__interrupt void adc_isr(void);

// RV335
void adc_isr(void);

• Differences in interrupt configuration and startup process between TI and RV335

// Ti
DINT; // Disable CPU interrupt
InitPieCtrl(); // initialize pie control registers
IER = 0x0; // Disable CPU interrupt
IFR = 0x0; // Clear cpu interrupt flags
EALLOW;
PieVectTable.EPWM1_INT = &epwm1_int_isr; // config isr
EDIS;
IER |= M_INT3; // Enable CPU INT
PieCtrlRegs.PIECTRL.bit.ENPIE = 1; // Enable the PIE
PieCtrlRegs.PIEIER3.bit.INTx1 = 1;
EINT; // Enable Global interrupt INTM
ERTM; // Enable Global realtime interrupt DBGM

3.3. C language features

• Different ways to assign code sections: TI uses “#pragma CODE_SECTION” for section mapping, while RV335 uses the “__attribute__” keyword in function declaration.

// Ti
#pragma CODE_SECTION(func, " .section")
void func(void) {// some code}

// RV335
void __attribute__((section(".section "))) func(void) {// some code}

• TI uses its platform-specific cmd file as the linker script, while RV335 uses a standard C-format linker script.

4. Known chip issues

4.1. Some boot modes exist

FDM320RV335 has 16 boot modes. The boot modes are consistent with competing chips, as shown in the table below.

Table 4-1 Chip boot differences

Mode GPIO87/XA15 GPIO86/XA14 GPIO85/XA13 GPIO84/XA12 Description

F 1 1 1 1 Jump to flash  
E 1 1 1 0 SCI-A boot  
D 1 1 0 1 SPI-A boot  
C 1 1 0 0 I2C-A boot  
B 1 0 1 1 eCAN-A boot  
A 1 0 1 0 McBSP-A boot  
9 1 0 0 1 Jump to XINTF x16  
8 1 0 0 0 Jump to XINTF x32  
7 0 1 1 1 Jump to OTP  
6 0 1 1 0 Parallel GPIO I/O boot  
5 0 1 0 1 Parallel XINTF boot  
4 0 1 0 0 Jump to SARAM  
3 0 0 1 1 Branch to check boot mode  
2 0 0 1 0 Jump to flash, skip ADC calibration  
1 0 0 0 1 Jump to SARAM, skip ADC calibration  
0 0 0 0 0 Jump to SCI, skip ADC calibration  

For FDM320RV335 chips with silicon version A, when boot mode 0 (jump to SCI, skip ADC calibration) is set, there are issues with SCI send/receive communication when using a simulator. This boot mode should be avoided; other boot modes such as SPI, I2C, eCAN, McBSP are not affected.

When boot mode is 3, the simulator cannot be connected, so this mode should be avoided.

4.2. JTAG cannot wake up the processor from standby mode

When the FDM320RV335 chip is in standby mode, it cannot be awakened using the Debug module. Avoid using the Debug module to wake up standby mode.

4.3. Timer module

4.3.1. Timer initialization

After timer initialization, during the first operation, the setting time of the TIF bit in the TIMERxTCR register will exceed the expected value by about ten timer clock cycles.

Users need to evaluate the impact of this difference on the system.

4.3.2. Timer TIMERxTIM register

When the timer module clock is configured to system clock divided by 1, after clearing the TIMERxTIMH:TIMERxTIM register, it will immediately reload the value from the TIMERxPRDH:TIMERxPRD register.

4.4. Abnormal connection to simulator after watchdog reset

When the watchdog module triggers a system reset during simulator debugging, the simulator disconnects, and the IDE displays “hart reset”.

4.5. Event capture module eCAP

4.5.1. Initialize eCAP

When initializing eCAP registers on the FDM320RV335 chip, the configuration of the TSCTRSTOP bit in the ECCTL2 register and the CAPLDEN bit in the ECCTL1 register should be placed at the end of the initialization program to ensure correct values in the CAP4-1 capture registers.

4.5.2. APWM mode

When configuring the eCAP module in APWM mode on the FDM320RV335 chip, if the pulse period is set to T and the positive pulse width to P, the actual output waveform will have a period of T+1 and a positive pulse width of P+1.

In the current version of the FDM320RV335 chip, when the eCAP module is configured in APWM synchronization mode, the output waveform is abnormal. This mode should be avoided in design.

4.6. Quadrature encoder pulse eQEP interface

4.6.1. eQEP synchronization mode

In the FDM320RV335 chip, after configuring the eQEP module in synchronous output mode, the pulse width of the synchronization signal output on the S pin is 300 ns longer than that of competing chips.

4.6.2. eQEP interrupt flag setting

In the FDM320RV335 chip, after multiplexing GPIO as eQEP function, the SEL bit of the QFLG register will be set. It needs to be cleared before use.

4.7. Pulse width modulation ePWM module

4.7.1. Clock division

In the FDM320RV335 chip, in Debug mode, software breakpoints may affect the PWM waveform, while full-speed operation produces normal PWM waveforms.

4.7.2. Hardware synchronization issue

In the FDM320RV335 chip, when the ePWM module is configured in hardware synchronization mode, when the ePWMSYNCI input is valid, the synchronization phase is unstable, with a one TBCLK error.

4.7.3. First waveform abnormality

In the FDM320RV335 chip, after initialization configuration of the ePWM module, the waveform output in the first cycle is abnormal.

4.8. Different FREESOFT modes affect functionality

In the FDM320RV335 chip, different configurations of the FREESOFT bit in peripheral modules affect functionality during breakpoint debugging in Debug mode.

For example, if the FREESOFT bit of the McBSP module is configured as 00, functionality testing during breakpoint debugging is abnormal. It needs to be configured to mode 10 for normal breakpoint debugging.
